\title{GwenLaya v4: a pre-registered study of answering only when a check can back the answer\\[4pt]
\large Interim report after the first night run: registered design, deviations,\\
one descriptive single-arm result, and no completed pre-registered test}
\author{Xavier Callens\\AutoevolveAI / ANSE open-source project}
\date{8 October 2026 \quad (draft v4.0, branch \texttt{night/2026-10-07})}

\maketitle

\begin{abstract}
GwenLaya is a system design in which a small open model (Qwen3.5 family) answers a programming or
mathematics question only when an executed check or a calibrated confidence score supports the
answer, and otherwise abstains or escalates to a larger tier. We pre-registered fifteen hypotheses
(two primary: fewer confident-wrong answers than log-probability selective prediction at matched
coverage, H1; lower cost per correct answered item than always using the largest tier with the
gate, H3) before any GwenLaya run. This report covers the first, budget-limited night run.
\textbf{No pre-registered hypothesis test was completed.} The only scored data are 80 items from
one arm that is not a registered arm (Qwen3.5-2B, q4\_K\_M, CPU, no gate, no calibrator). Only the
28 Python items are usable as a descriptive result: 11/28 passed the hidden checks (pass rate
0.393, 95\% cluster bootstrap CI 0.214--0.571) while the raw $\exp(\text{mean log-prob})$
confidence averaged 0.896, so it was badly calibrated (ECE 0.519, CI 0.392--0.689); its AUROC was
0.717 with a CI (0.483--0.917) that includes 0.5. These are descriptive numbers on public
benchmarks that Qwen3.5 has probably seen in pretraining, not tests. The 26 math items are invalid
(a prompt-path defect, and an unregistered last-number answer extraction), and the 26 Rust items
come from a harness that has not been validated; numbers pooled over all 80 items are shown only as
a labelled sensitivity analysis. The budget hypothesis (H13) is not refuted on an interim basis
(known spend \$0.00, 2,706 TPU-seconds unpriced), but the spend ledger enforces it by construction,
so this is not evidence about the system. Review also found that the HumanEval+ gate payloads of the
night task files contained the hidden tests; no gate ran, so no number is affected, and the files
have been rebuilt (D25). We also report a TPU feasibility finding (Qwen2.5 generation works on a v5e chip
via vLLM's TPU build; Qwen3.5 did not load in time; no TPU LoRA path was found for Qwen3.5 dense
or Qwen3.8), the GCP spend actually recorded, and every deviation from the registration. We
begin by restating the retraction of a v3 claim and the failed v3 gate.
\end{abstract}

\section{Retraction and the v3 gate failure, stated first}\label{sec:retraction}

\paragraph{Retraction.} Revision 3.1.0 of the predecessor report~\cite{gwayav3} claimed that the
low-tier optimizer improved pass rates by at least $+8.0$ percentage points. That claim rested on a
hand-written results file with invented numbers (A0 33\,\%, A3 100\,\%). The file was fabricated, it
has been deleted, and it is not evidence (\code{results/PREREGISTRATION.md}). The claim is
retracted. Nothing in this paper depends on it.

\paragraph{The measured v3 gate failed.} The pre-registered v3 gate was
$\text{A3}-\text{A0}\ge +8.0$ points pass@1 on MBPP-sanitized with \code{qwen2.5-coder:1.5b}. Both
measured runs \textbf{FAIL} that gate:
\begin{itemize}
\item $n=60$, CPU: A3$-$A0 $=+6.67$ points, 95\% CI $[1.67, 13.33]$, 4 gained / 0 lost, exact
  McNemar $p=0.125$; verdict FAIL (\code{results/results_n60_cpu.json}).
\item $n=257$, L4 GPU: A0 64.2\,\%, A3 71.98\,\%, A3$-$A0 $=+7.78$ points, 95\% CI $[4.67, 11.28]$,
  20 gained / 0 lost; verdict FAIL against $+8.0$. This file's \code{git_commit} field is empty
  (\code{results/results_n257_l4_gpu.json}).
\end{itemize}
At $n=60$ the difference is not significant by the exact McNemar test ($p=0.125$, 4/0
discordant pairs); the percentile-bootstrap interval there is not informative, because when every
discordant pair favours A3 a resample can reach $\Delta\le 0$ only by drawing no discordant item at
all, so its lower bound is positive almost by construction. Only the $n=257$ run (20/0 discordant;
the file rounds the exact McNemar $p$ to 0.0, i.e.\ $p<0.001$) supports a nonzero effect. In both
runs the registered $+8.0$ threshold was missed, and we report both as FAIL. The same file shows the v3 gate's weakness that motivates
v4: of answers the gate called VERIFIED (coverage 80.93\,\%), only 88.94\,\% passed the hidden
tests. By arithmetic on those two file values (not a measurement), about 8.95\,\% of all problems
were confident-wrong under v3.

\section{What GwenLaya is and what was registered}\label{sec:design}

The full registration is \code{docs/GWENLAYA_PREREGISTRATION.md} (revision 2, design freeze; sha256
of each revision in \code{docs/PREREG_FREEZE.txt}). In brief:

\begin{itemize}
\item \textbf{System (GL).} Generate with a small Qwen3.5 tier; run a \emph{gate-visible} executed
  check that, by design, never sees the scoring tests (in the night task files this was violated
  for HumanEval+, whose gate payloads contained the whole hidden suite; no gate ran, and the files
  were rebuilt, D25, Section~\ref{sec:defects}); score the candidate with a calibrated confidence head
  (a LoRA head on the \code{convaiinnovations/laya} encoder); answer VERIFIED, LIKELY\_CORRECT($p$),
  abstain, or escalate to a larger tier. The label for calibration is the outcome on the
  \emph{hidden} checks, so VERIFIED is never treated as ground truth.
\item \textbf{Eval pool E.} HumanEval+ and MBPP+~\cite{evalplus} (Python, 542 items), MultiPL-E
  Rust~\cite{multiple} (510), MATH-500~\cite{math,letsverify} (500), and miniF2F Lean 4 (244,
  outside the pooled analysis).
\item \textbf{Arms.} B1 smallest tier alone; B2 largest tier alone; B3 log-probability selective
  prediction~\cite{selective}; B4 self-consistency; B5 largest tier with the v3-style gate only;
  B6 Laya zero-shot; LR and a shuffled-label negative control SH.
\item \textbf{Primary family} (Holm~\cite{holm}, $m=2$; a primary that does not run enters with
  $p=1$, so the other is tested at 0.025): H1, CWR(GL)$-$CWR(B3) at matched coverage,
  exact one-sided McNemar~\cite{mcnemar} plus a cluster-stratified paired bootstrap, MEI 3.0 points;
  H3, cost per correct answered item, GL vs B5, MEI 25\,\% reduction, with answered accuracy
  non-inferior by 2.0 points.
\item \textbf{Secondary:} calibration (H4 ECE~\cite{guo}, H5 Laya vs LR AUROC, H6 split-conformal
  selective error~\cite{conformal}); quantization (H8); training (H9); systems (H13 budget, H14
  endpoint latency, H15 preemption). \textbf{Exploratory:} H2, H7, H10--H12.
\end{itemize}
Hypothesis wording and MEIs are unchanged. The H3 cost unit (D3), the H5 comparator (D5, if the
frozen-embedding probe replaces the LoRA head) and the size of the primary Holm family (D22, made
after the L2 generations existed and reverted to the registered $m=2$ in D26) are deviations.
Throughout, VERIFIED keeps its registered meaning (all gate-visible checks passed); the outcome on
the hidden checks is written PASS\_HIDDEN / FAIL\_HIDDEN / UNDECIDED.

\paragraph{Benchmarks reduced.} To stay within budget and wall clock we ran no benchmark beyond the
three primary domains, on 80 of their 1,541 included items, with two tiers instead of four. Lean 4,
GSM8K, AIME25, LiveCodeBench, the MBPP continuity anchor, the 0.8B tier, self-consistency and the
second seed were dropped (D7--D10). The registered design for all of them stays in the
registration and is not reported here as if it had run.

\paragraph{Power was known to be insufficient before generation.} The freeze addendum computed the
power of H1's exact McNemar test at $n=80$ before any item was generated: 0.052 at the 3-point MEI
and 0.261 at a 6-point effect ($\alpha=0.025$). A non-significant H1 at this $n$ would therefore
have been inconclusive, not evidence of no effect.

\paragraph{What actually ran.} L0 (environment, throughput), L1 (manifest, freeze addendum,
decontamination), L2 (2B generation on all 80 E-night items, 72 minutes wall), and scoring of those
80 generations. L3 (4B generation) was held because the L2 review found a blocking defect
(Section~\ref{sec:defects}). G1 (GPU) and E1 (endpoint) never ran: the GPU slot never freed. No
Laya head, calibrator, threshold or second arm exists.

\paragraph{H13 (budget).} Decision rule: ledger total $\le\$40$ planned and $\le\$50$ hard, and no

the verdict is interim. An earlier draft of this report gave $P(\text{true})=0.97$; that was author

\paragraph{H15 (preemption).} \code{tests/test_run_study.py::test_resume_after_kill_mid_run}
passes, but it simulates a death by appending a torn line; it sends no SIGKILL and measures no lost
wall time. It is weak support that resume is item-granular, not the registered verification, so the
probability stays at the prior.

The scored arm \code{base} is Qwen3.5-2B q4\_K\_M on llama.cpp~\cite{llamacpp}, greedy, thinking off,

registered arms. Confidence is the raw $\exp(\text{mean token log-prob})$, uncalibrated and not
cross-fitted. Intervals are 95\% cluster-stratified bootstrap percentile intervals (10,000

\paragraph{Why Python is the headline.} Pooling the three domains would mix one usable domain with
two that are not (Section~\ref{sec:defects}): the 26 math generations are invalid, and the 26 Rust

AUROC or ECE would then describe domain composition and defects, not the confidence signal. We
therefore report Python ($n=28$) as the headline and show every other number only as a labelled
row of Table~\ref{tab:calib}.

\paragraph{Python.} 11 of 28 items passed the hidden checks and 17 failed (0 undecided), a pass
rate of 0.393 (CI 0.214--0.571). The mean raw confidence was 0.896 (CI 0.875--0.917), so the score
is badly calibrated (ECE 0.519, CI 0.392--0.689; Brier 0.476, CI 0.334--0.617). The AUROC point
estimate was 0.717 (AURC 0.438, CI 0.221--0.712), but its interval (0.483--0.917) includes 0.5, so with $n=28$ we cannot say that it ranks correct answers above wrong
ones. The confident-wrong rate, counting every answered item that did not pass, was 0.607 (CI
0.429--0.786). Cost per passing item was 330 server CPU-seconds (CI 174--726).

\paragraph{Rust and math (not interpretable).} Rust: 0 PASS\_HIDDEN, 13 FAIL\_HIDDEN, 13 UNDECIDED.
Math: 3 PASS\_HIDDEN, 18 FAIL\_HIDDEN, 5 UNDECIDED as scored; all 26 math answers were extracted by
the unregistered last-number fallback (0 contained \verb|\boxed|), including all 3 passes, and under
the registered boxed-only rule math passes 0/26. Pooled over 80 items the pass rate is 0.175 as
scored and 0.138 with boxed-only math. The pooled AUROC changes from 0.618 to 0.758 when only the
scoring rule of the invalid math subset changes, which is why we do not interpret it.

\paragraph{Contamination.} HumanEval+, MBPP+, MultiPL-E and MATH-500 are public and were very
probably seen in Qwen3.5 pretraining (registration Section~10, ``Residual risk, stated''). The
absolute pass rates above are therefore not clean capability estimates; the registration claims
only paired, within-model deltas, and none was measured. Memorised items would also tend to have
high log-probability and pass, which can inflate AUROC differently by score type (review finding
F12).

What we read from this, and no more: on 28 Python items the raw log-probability of a 2B model at q4
sits near 0.9 while about 0.4 of the answers pass, so it is not usable as a probability without
calibration. This is consistent with the motivation for a calibrated head, but it does not test H1,
H4 or H5.

\subsection{Defects found, and why some numbers are invalid}\label{sec:defects}

\begin{enumerate}
\item \textbf{Math prompt path (blocking).} All 26 math completions were produced with the Python
  code system prompt and a \verb|```python| prefill, because the prompt builder falls back to the
  \code{python} tag for any domain it does not list. 0 of 26 contain \verb|\boxed|. The frozen user
  prompt asked for a boxed answer, but the system prompt and prefill overrode it. The math pass
  rate says nothing about the model's math ability. The fix (math system prompt, no code prefill)
  and a regeneration of the 26 items must be logged as a new deviation before any rerun; neither has
  happened yet.
\item \textbf{Unregistered math answer extraction (D24).} The registration scores the boxed answer
  and treats unparseable math output as UNVERIFIED (fail-closed). The scorer
  (\code{math_check.extract_final_answer}) instead tries the last \verb|\boxed|, then a
  \texttt{\#\#\#\#} line, then the last number anywhere in the text. With no boxed output, all 26 math
  items were scored by the last number; the 3 passes came from text ending in Python comments, a
  \code{print} call or a \code{return} statement. We now report both versions (Table~\ref{tab:calib})
  and froze the registered boxed-only rule before the math regeneration
  (\code{docs/FREEZE_ADDENDUM_2026-10-08_D25.md}).
\item \textbf{Rust harness unvalidated.} MultiPL-E has no reference solutions, so the Rust harness
  was checked only by typechecking test bodies (D17). 0/26 PASS\_HIDDEN with 13/26 UNDECIDED is as
  consistent with a harness or toolchain problem as with model weakness. Until one known-good Rust
  program passes end to end, the Rust rate is unverified.
\item \textbf{Gate not recorded.} The \code{gate} field is null in every scored row, so no
  registered VERIFIED exists in this run and VERIFIED precision against hidden checks (H7) cannot
  be computed.
\item \textbf{Hidden tests in the HumanEval+ gate payload (D25).} The task builder restricted the
  HumanEval+ gate by rewriting only the loop header (\code{zip(inputs[:1], results[:1])}), so the
  complete hidden \code{inputs} and \code{results} lists stayed in every HumanEval+ gate payload
  (11/11 E-night rows, 161/161 primary rows; four primary items also carried a reference
  implementation). A candidate executed in the same process as \code{check()} could have read them,
  and any component that reads the gate payload would have seen the hidden answers. MBPP+, Rust and
  math gate payloads were correctly restricted. The statement that the gate ``never sees the scoring
  checks'' was therefore false for HumanEval+ in the night files. \textbf{No reported number changes}:
  the L2 run executed no gate. The builder now rewrites the literals themselves with an AST
  transform, fails closed, and is covered by a test asserting that no hidden element appears in a
  gate payload. The task files were rebuilt with prompts and hidden checks unchanged (E-night 80
  items; primary E 1,536 items after 5 fail-closed exclusions; hashes in
  Section~\ref{sec:repro}).
\end{enumerate}

\paragraph{What ``passed'' means in this paper.} An item is PASS\_HIDDEN only if it passed the named
hidden checks: for Python, the full EvalPlus test suite run in a bubblewrap sandbox; for Rust,
compilation and all \code{assert_eq!} lines of the MultiPL-E test with \code{rustc}; for math, a
sympy/numeric equivalence check between the gold answer and the answer extracted as described in
item 2 above (boxed, else \texttt{\#\#\#\#}, else last number). It means nothing more. It does not mean
the solution is correct on other inputs, and for Rust the harness itself is not yet validated.

\section{TPU feasibility finding}\label{sec:tpu}

Because the GPU slot was unavailable, we tested whether a Cloud TPU v5e could replace it. Two
smoke runs were made on a single-chip v5litepod-1 (logs under
\url{gs://socrateai-datalake-gen-lang-client-0625573011/gwenlaya_v4/tpu_smoke/gwenlaya-tpu-smoke-215529/}).
The first, on a spot VM, was preempted after about 4 minutes with no results. The second, on demand:

\begin{itemize}
\item \textbf{Qwen2.5 works.} \code{Qwen/Qwen2.5-Coder-1.5B-Instruct} loaded and generated with
  vLLM~\cite{vllm} 0.31.0's TPU backend (load 208.9 s; 442 completion tokens in 0.61 s,
  724.6 tok/s batched throughput; \code{res_qwen25.json}). The GWAYA gate on that VM returned UNVERIFIED for
  every item because bubblewrap was not available there, i.e.\ it failed closed as designed; no
  correctness number came out of this run.
\item \textbf{Qwen3.5 is unproven on TPU.} \code{Qwen/Qwen3.5-4B} resolved to
  \code{Qwen3_5ForConditionalGeneration} but did not finish loading/compiling within the 1,500 s
  step limit (exit 124). We did not show that it works or that it cannot work.
\item \textbf{No TPU LoRA path was found for Qwen3.5 dense or Qwen3.8.} Serving Qwen2.5 with
  \code{enable_lora} failed at engine initialisation. The JAX training stacks we inspected list
  Qwen2/Qwen3 (Tunix 0.1.7) and Qwen2.5/Qwen3 plus Qwen3.5 mixture-of-experts scripts (MaxText), but
  no dense Qwen3.5 or Qwen3.8 path. GwenLaya's training steps (Laya head, SFT) therefore stay on the
  GPU/CPU plan.
\end{itemize}

\section{Limitations}\label{sec:limits}

\begin{itemize}
\item No pre-registered test ran. Nothing here supports or refutes H1--H12, H14 or H15.
\item The only scored arm is unregistered, single-seed, $n=80$, on CPU, with no gate recorded.
\item The math generations are invalid (prompt-path defect) and were scored with an unregistered
  last-number extraction (D24); the Rust harness is unvalidated. Only the 28 Python items are a
  usable descriptive result, and with $n=28$ their AUROC interval includes 0.5.
\item \textbf{Contamination.} All absolute scores are on public sets (HumanEval+, MBPP+,
  MultiPL-E, MATH-500) that Qwen3.5 has probably seen in pretraining; they are not clean capability
  estimates, and only paired within-model deltas are claimed by the registration. Decontamination
  (D18) covered only training/calibration data against E and cannot detect pretraining exposure. The
  contamination-stratified analysis asked for by review finding F12 (for example MBPP+ versus
  HumanEval+ items, or a post-cutoff anchor such as LiveCodeBench, which D10 dropped) was not done:
  \TBD.
\item The HumanEval+ gate payloads of the night task files contained the hidden tests (D25). No gate
  ran in L2, so no result is affected, but any earlier claim that the gate never saw the scoring
  checks was false for those files.
\item Several deviations (D22--D26) were written after the L2 generations existed; none was written
  after a registered test, because none ran.
\item Even with all arms present, $n=80$ gives H1 power of about 0.05 at its MEI; the night design
  could at best produce an inconclusive H1.
\item Cost is server CPU-seconds on a machine shared with foreign jobs and includes idle threads; it
  is not comparable to the registered L4 GPU-seconds.
\item Two ledger lines are unpriced and lack the \code{resource} field; the USD spend above is a
  lower bound, and H13 holds largely by construction of the ledger.
\item Scored rows are not yet mirrored to the data lake as the registration requires.
\item Lean 4, the training arms, quantization and the endpoint were not run. The TPU finding is from
  one chip, one vLLM version and a fixed time limit.
\end{itemize}
