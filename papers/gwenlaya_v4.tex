\begin{abstract}
GwenLaya is a system design in which a small open model (Qwen3.5 family) answers a programming or
mathematics question only when an executed check or a calibrated confidence score supports the
answer, and otherwise abstains or escalates to a larger tier. We pre-registered fifteen hypotheses
(two primary: fewer confident-wrong answers than log-probability selective prediction at matched
coverage, H1; lower cost per correct answered item than always using the largest tier with the
gate, H3) before any GwenLaya run. This report covers the first, budget-limited night run.
\textbf{No pre-registered hypothesis test was completed.} The scored night data are 80 items from
one arm that is not a registered arm (Qwen3.5-2B, q4\_K\_M, CPU, no gate, no calibrator).
\textbf{Revision v3.3.1 corrects v3.3.0} (Section~\ref{sec:corrections}): the v3.3.0 Rust result
(0/26) was an artefact of our sandbox, in which no Rust program could link (D27); after the fix,
and a check of the harness on hand-written correct and wrong solutions, the same 26 Rust
generations pass the hidden checks in 6 cases. Python is unchanged: 11/28 passed the hidden checks
(pass rate 0.393, 95\% cluster bootstrap CI 0.214--0.571) while the raw
$\exp(\text{mean log-prob})$ confidence averaged 0.896, so it was badly calibrated (ECE 0.519, CI
0.392--0.689); its AUROC was 0.717 with a CI (0.483--0.917) that includes 0.5. The 26 night math
generations remain invalid (they went through the code prompt path, D28) and none passes under the
registered boxed-only rule. These are descriptive numbers on public benchmarks that the models
have probably seen in pretraining, not tests. We also report a descriptive, unregistered TPU run
(one v5e chip, greedy, one sample) of Qwen3.5-2B, Qwen3.5-4B and Qwen2.5-Coder-1.5B on the same 80
tasks, re-scored on our machine because scoring on the TPU host was invalid for Python; Qwen3.5-2B
in bf16 on TPU gives the same Python and Rust pass counts as the q4 CPU arm (not the same items in
every case), a consistency check rather than a test. The budget hypothesis (H13) is not refuted on an
interim basis (recorded spend \$1.54, estimated from catalog list prices), but the spend ledger
enforces it by construction, so this is not evidence about the system. Review also found that the
HumanEval+ gate payloads of the night task files contained the hidden tests; no gate ran, so no
number is affected, and the files have been rebuilt (D25). No TPU LoRA path was found for dense
Qwen3.5 or Qwen3.8. We report the GCP spend actually recorded and every deviation from the
registration, and begin by restating the retraction of a v3 claim and the failed v3 gate.
\end{abstract}

\section{Retraction and the v3 gate failure, stated first}\label{sec:retraction}

\paragraph{Retraction.} Revision 3.1.0 of the predecessor report~\cite{gwayav3} claimed that the
low-tier optimizer improved pass rates by at least $+8.0$ percentage points. That claim rested on a
hand-written results file with invented numbers (A0 33\,\%, A3 100\,\%). The file was fabricated, it
has been deleted, and it is not evidence (\code{results/PREREGISTRATION.md}). The claim is
retracted. Nothing in this paper depends on it.

\paragraph{The measured v3 gate failed.} The pre-registered v3 gate was
$\text{A3}-\text{A0}\ge +8.0$ points pass@1 on MBPP-sanitized with \code{qwen2.5-coder:1.5b}. Both
measured runs \textbf{FAIL} that gate:
\begin{itemize}
\item $n=60$, CPU: A3$-$A0 $=+6.67$ points, 95\% CI $[1.67, 13.33]$, 4 gained / 0 lost, exact
  McNemar $p=0.125$; verdict FAIL (\code{results/results_n60_cpu.json}).
\item $n=257$, L4 GPU: A0 64.2\,\%, A3 71.98\,\%, A3$-$A0 $=+7.78$ points, 95\% CI $[4.67, 11.28]$,
  20 gained / 0 lost; verdict FAIL against $+8.0$. This file's \code{git_commit} field is empty
  (\code{results/results_n257_l4_gpu.json}).
\end{itemize}
At $n=60$ the difference is not significant by the exact McNemar test ($p=0.125$, 4/0
discordant pairs); the percentile-bootstrap interval there is not informative, because when every
discordant pair favours A3 a resample can reach $\Delta\le 0$ only by drawing no discordant item at
all, so its lower bound is positive almost by construction. Only the $n=257$ run (20/0 discordant;
the file rounds the exact McNemar $p$ to 0.0, i.e.\ $p<0.001$) supports a nonzero effect. In both
runs the registered $+8.0$ threshold was missed, and we report both as FAIL. The same file shows the v3 gate's weakness that motivates
v4: of answers the gate called VERIFIED (coverage 80.93\,\%), only 88.94\,\% passed the hidden
tests. By arithmetic on those two file values (not a measurement), about 8.95\,\% of all problems
were confident-wrong under v3.

\section{Corrections in v3.3.1}\label{sec:corrections}

Revision v3.3.0 of this report contained a wrong Rust result caused by our own harness. This
revision corrects it and records four new deviations (D27--D30, Table~\ref{tab:dev}). All were
found and fixed after the night generations existed; no registered test has run, so none was
written with a test result in view.

\begin{itemize}
\item \textbf{D27, Rust harness (v3.3.0 Rust result withdrawn).} Inside the bubblewrap sandbox,
  \code{rustc}'s linker \code{cc} resolves through \code{/etc/alternatives}, which the sandbox did
  not mount, so \emph{every} Rust program failed to link. The v3.3.0 Rust result (0/26 passing the
  hidden checks) was therefore a harness artefact, not a model result. While fixing it we also found
  that the harness wrote its pass nonce into \code{main.rs}, so a candidate could read its own source
  or binary and forge a pass; we reproduced this and closed it (nonce passed on stdin; separate
  compile and run sandboxes; no \code{/proc} in the run sandbox; \code{unsafe},
  \code{link_section} and \code{asm} rejected). \code{assert_ne!} lines are now counted alongside
  \code{assert_eq!}. Validation (\code{results/gwenlaya_v4/rust_harness_validation.json}):
  hand-written reference solutions for 25 of the 26 night Rust tasks all pass (25/25), and 9
  deliberately wrong solutions all fail (9/9). Re-scoring the unchanged night generations gives
  Rust 6/26 passing the hidden checks (Section~\ref{sec:results}). The compile failures that were
  examined are model errors (for example indexing a \code{str} by \code{usize}, or calling a
  non-existent \code{.unique()} method).
\item \textbf{D28, math prompt path and scoring.} The night math generations went through the code
  path (Python system prompt, \verb|```python| prefill, \verb|```| stop), so they remain invalid;
  this conclusion is unchanged. The code is fixed for future runs: a prose math prompt ending in
  \verb|\boxed{}|, non-thinking mode for Qwen3.x through an empty think block, and the registered
  boxed-only rule as the scoring default (the last-number fallback of D24 is now opt-in only).
  Under boxed-only, all 26 night math generations are UNDECIDED (none contains \verb|\boxed|). A
  self-consistency key bug (the math vote key used the extraction method instead of the answer) was
  also fixed; self-consistency (B4) did not run (D9), so no reported number is affected.
\item \textbf{D29, Python harness environment.} With a \code{uv}-managed interpreter the venv's
  \code{python} symlink chain passed through a directory not bound into the sandbox, so Python could
  not start inside bubblewrap on the re-scoring machine. Fixed by recreating the interpreter
  symlinks. The Python result is unchanged (11/28).
\item \textbf{D30, TPU scoring and an unregistered TPU run.} A third TPU run generated all 80 night
  tasks for three models (Section~\ref{sec:tpurun}). Python scoring launched from inside the vLLM
  process on the TPU host failed for every item, so all TPU generations were re-scored on our machine
  with the same checkers. This run is descriptive and was not a registered arm.
\end{itemize}

\section{What GwenLaya is and what was registered}\label{sec:design}

The full registration is \code{docs/GWENLAYA_PREREGISTRATION.md} (revision 2, design freeze; sha256
of each revision in \code{docs/PREREG_FREEZE.txt}). In brief:

\begin{itemize}
\item \textbf{System (GL).} Generate with a small Qwen3.5 tier; run a \emph{gate-visible} executed
  check that, by design, never sees the scoring tests (in the night task files this was violated
  for HumanEval+, whose gate payloads contained the whole hidden suite; no gate ran, and the files
  were rebuilt, D25, Section~\ref{sec:defects}); score the candidate with a calibrated confidence head
  (a LoRA head on the \code{convaiinnovations/laya} encoder); answer VERIFIED, LIKELY\_CORRECT($p$),
  abstain, or escalate to a larger tier. The label for calibration is the outcome on the
  \emph{hidden} checks, so VERIFIED is never treated as ground truth.
\item \textbf{Eval pool E.} HumanEval+ and MBPP+~\cite{evalplus} (Python, 542 items), MultiPL-E
  Rust~\cite{multiple} (510), MATH-500~\cite{math,letsverify} (500), and miniF2F Lean 4 (244,
  outside the pooled analysis).
\item \textbf{Arms.} B1 smallest tier alone; B2 largest tier alone; B3 log-probability selective
  prediction~\cite{selective}; B4 self-consistency; B5 largest tier with the v3-style gate only;
  B6 Laya zero-shot; LR and a shuffled-label negative control SH.
\item \textbf{Primary family} (Holm~\cite{holm}, $m=2$; a primary that does not run enters with
  $p=1$, so the other is tested at 0.025): H1, CWR(GL)$-$CWR(B3) at matched coverage,
  exact one-sided McNemar~\cite{mcnemar} plus a cluster-stratified paired bootstrap, MEI 3.0 points;
  H3, cost per correct answered item, GL vs B5, MEI 25\,\% reduction, with answered accuracy
  non-inferior by 2.0 points.
\item \textbf{Secondary:} calibration (H4 ECE~\cite{guo}, H5 Laya vs LR AUROC, H6 split-conformal
  selective error~\cite{conformal}); quantization (H8); training (H9); systems (H13 budget, H14
  endpoint latency, H15 preemption). \textbf{Exploratory:} H2, H7, H10--H12.
\end{itemize}
Hypothesis wording and MEIs are unchanged. The H3 cost unit (D3), the H5 comparator (D5, if the
frozen-embedding probe replaces the LoRA head) and the size of the primary Holm family (D22, made
after the L2 generations existed and reverted to the registered $m=2$ in D26) are deviations.
Throughout, VERIFIED keeps its registered meaning (all gate-visible checks passed); the outcome on
the hidden checks is written PASS\_HIDDEN / FAIL\_HIDDEN / UNDECIDED.

\section{The night run and its deviations}\label{sec:deviations}

the total GCP budget (\$50 hard, \$45 working ceiling for this programme, \$40 planned), and the
fact that the project's only GPU quota unit (\code{GPUS_ALL_REGIONS} limit 1) was held all night by
a VM that is not part of this project and that we did not touch. All generation therefore ran on a
shared 8-core CPU, and the scope was cut. Every deviation is in \code{docs/DEVIATIONS.md} and is

\paragraph{Benchmarks reduced.} To stay within budget and wall clock we ran no benchmark beyond the
three primary domains, on 80 of their 1,541 included items, with two tiers instead of four. Lean 4,
GSM8K, AIME25, LiveCodeBench, the MBPP continuity anchor, the 0.8B tier, self-consistency and the
second seed were dropped (D7--D10). The registered design for all of them stays in the
registration and is not reported here as if it had run.

\paragraph{Power was known to be insufficient before generation.} The freeze addendum computed the
power of H1's exact McNemar test at $n=80$ before any item was generated: 0.052 at the 3-point MEI
and 0.261 at a 6-point effect ($\alpha=0.025$). A non-significant H1 at this $n$ would therefore
have been inconclusive, not evidence of no effect.

\paragraph{What actually ran.} L0 (environment, throughput), L1 (manifest, freeze addendum,
decontamination), L2 (2B generation on all 80 E-night items, 72 minutes wall), and scoring of those
80 generations. L3 (4B generation) was held because the L2 review found a blocking defect
(Section~\ref{sec:defects}). G1 (GPU) and E1 (endpoint) never ran: the GPU slot never freed. No
Laya head, calibrator, threshold or second arm exists. After v3.3.0 the same 80 generations were
re-scored with the fixed harnesses (D27--D29; no new CPU generation), and an unregistered TPU run
generated the 80 tasks for three models (D30, Section~\ref{sec:tpurun}).

\paragraph{H13 (budget).} Decision rule: ledger total $\le\$40$ planned and $\le\$50$ hard, and no

priced on 2026-10-08 from the Cloud Billing Catalog list prices (on-demand v5e \$1.20 per

the planned GCS ledger \code{runs/LEDGER.jsonl} does not exist, and later nights will add spend, so

wall time. It is weak support that resume is item-granular, not the registered verification, so the
probability stays at the prior.

\subsection{Descriptive single-arm result (not a pre-registered test)}

The scored arm \code{base} is Qwen3.5-2B q4\_K\_M on llama.cpp~\cite{llamacpp}, greedy, thinking off,
\code{max_new_tokens} 1024, with no gate, no calibrator and no escalation. It is not one of the
registered arms. Confidence is the raw $\exp(\text{mean token log-prob})$, uncalibrated and not
cross-fitted. Intervals are 95\% cluster-stratified bootstrap percentile intervals (10,000
resamples, seed 0). Every number below is read from \code{papers/numbers_v4.json}
(\code{single_arm.by_domain.*}, \code{single_arm.boxed_only.*}, \code{arm.base.*}), written by
\code{scripts/analyze_study.py}; its tables are reproduced unedited in Appendix~\ref{app:tables}.
In v3.3.1 these files were regenerated from the re-scored rows
\code{results/gwenlaya_v4/night_L2fix/rows.jsonl} (same generations as v3.3.0, fixed Rust harness,
boxed-only math scoring; D27--D29).

\paragraph{Outcome labels.} The per-row outcome reported here is the result of the \emph{hidden}
checks: PASS\_HIDDEN, FAIL\_HIDDEN or UNDECIDED (\code{rows.jsonl} field \code{score} =
VERIFIED, FAILED or UNVERIFIED). It is \emph{not} the registered VERIFIED, which is the gate's
verdict on the gate-visible checks. The gate verdict was not recorded in any of the 80 rows
(\code{gate} is null in all of them), so this run contains no VERIFIED in the registered sense.

\paragraph{Why Python is the headline.} Pooling the three domains would mix usable domains with one
that is not (Section~\ref{sec:defects}): the 26 math generations are invalid, so a pooled AUROC or
ECE would partly describe that defect, not the confidence signal. Python ($n=28$) was chosen as the
headline in D26, before the Rust harness was fixed, and we keep that choice rather than change the
headline after seeing the re-scored Rust numbers. Rust ($n=26$) is now a second descriptive
domain, with the caveat that its harness was validated only after the generations were scored
(D27). Math and the pooled numbers appear only as labelled rows of Table~\ref{tab:calib}.

all 26 math items are UNDECIDED (0 PASS\_HIDDEN, 0 FAIL\_HIDDEN): none of the generations contains

that v3.3.0 reported as ``as scored'' (D24) is no longer applied. Pooled over 80 items the pass

\paragraph{Contamination.} HumanEval+, MBPP+, MultiPL-E and MATH-500 are public and were very
probably seen in Qwen3.5 pretraining (registration Section~10, ``Residual risk, stated''). The
absolute pass rates above are therefore not clean capability estimates; the registration claims
only paired, within-model deltas, and none was measured. Memorised items would also tend to have
high log-probability and pass, which can inflate AUROC differently by score type (review finding
F12).

What we read from this, and no more: on 28 Python and 26 Rust items the raw log-probability of a
2B model at q4 sits near 0.9 while well under half of the answers pass, so it is not usable as a
probability without calibration. This is consistent with the motivation for a calibrated head, but it does not test H1,
H4 or H5.

\subsection{Defects found, and why some numbers are invalid}\label{sec:defects}

\begin{enumerate}
\item \textbf{Math prompt path (blocking).} All 26 math completions were produced with the Python
  code system prompt and a \verb|```python| prefill, because the prompt builder falls back to the
  \code{python} tag for any domain it does not list. 0 of 26 contain \verb|\boxed|. The frozen user
  prompt asked for a boxed answer, but the system prompt and prefill overrode it. The math pass
  rate says nothing about the model's math ability. The fix (prose math prompt ending in
  \verb|\boxed{}|, no code prefill, Qwen3.x non-thinking) is now in the code and logged as D28. The
  26 night items have not been regenerated on CPU; the only math generations with the fixed prompt
  are those of the descriptive TPU run (Section~\ref{sec:tpurun}).
\item \textbf{Unregistered math answer extraction (D24).} The registration scores the boxed answer
  and treats unparseable math output as UNVERIFIED (fail-closed). The scorer
  (\code{math_check.extract_final_answer}) instead tries the last \verb|\boxed|, then a
  \texttt{\#\#\#\#} line, then the last number anywhere in the text. With no boxed output, all 26 math
  items were scored by the last number in v3.3.0, and the passes it produced came from text ending
  in Python comments, a \code{print} call or a \code{return} statement. We froze the registered
  boxed-only rule before any math regeneration (\code{docs/FREEZE_ADDENDUM_2026-10-08_D25.md}), and
  in v3.3.1 it is the scoring default; the fallback is opt-in only (D28).
\item \textbf{Rust harness (fixed in v3.3.1, D27).} MultiPL-E has no reference solutions, so the
  Rust harness was first checked only by typechecking test bodies (D17), which did not catch that no
  Rust program could link inside the sandbox. v3.3.0 reported the resulting 0/26 as a result; it was
  an artefact. The harness was also open to a nonce forgery. Both are fixed; the fixed harness passes
  25/25 hand-written correct solutions and fails 9/9 wrong ones on the night tasks
  (\code{results/gwenlaya_v4/rust_harness_validation.json}).
\item \textbf{Python harness environment (fixed, D29).} On the re-scoring machine a
  \code{uv}-managed interpreter could not start inside bubblewrap; fixed. The Python result is
  unchanged.
\item \textbf{Gate not recorded.} The \code{gate} field is null in every scored row, so no
  registered VERIFIED exists in this run and VERIFIED precision against hidden checks (H7) cannot
  be computed.
\item \textbf{Hidden tests in the HumanEval+ gate payload (D25).} The task builder restricted the
  HumanEval+ gate by rewriting only the loop header (\code{zip(inputs[:1], results[:1])}), so the
  complete hidden \code{inputs} and \code{results} lists stayed in every HumanEval+ gate payload
  (11/11 E-night rows, 161/161 primary rows; four primary items also carried a reference
  implementation). A candidate executed in the same process as \code{check()} could have read them,
  and any component that reads the gate payload would have seen the hidden answers. MBPP+, Rust and
  math gate payloads were correctly restricted. The statement that the gate ``never sees the scoring
  checks'' was therefore false for HumanEval+ in the night files. \textbf{No reported number changes}:
  the L2 run executed no gate. The builder now rewrites the literals themselves with an AST
  transform, fails closed, and is covered by a test asserting that no hidden element appears in a
  gate payload. The task files were rebuilt with prompts and hidden checks unchanged (E-night 80
  items; primary E 1,536 items after 5 fail-closed exclusions; hashes in
  Section~\ref{sec:repro}).
\end{enumerate}

\paragraph{What ``passed'' means in this paper.} An item is PASS\_HIDDEN only if it passed the named
hidden checks: for Python, the full EvalPlus test suite run in a bubblewrap sandbox; for Rust,
compilation with \code{rustc} and all \code{assert_eq!}/\code{assert_ne!} lines of the MultiPL-E
test, run in a separate sandbox (D27); for math, a sympy/numeric equivalence check between the gold
answer and the last \verb|\boxed{}| answer, with no \verb|\boxed| counted as UNDECIDED (D28). It
means nothing more. It does not mean the solution is correct on other inputs.

\section{TPU feasibility finding}\label{sec:tpu}

Because the GPU slot was unavailable, we tested whether a Cloud TPU v5e could replace it. Two
smoke runs (run \#1) were made on a single-chip v5litepod-1 (logs under
\url{gs://socrateai-datalake-gen-lang-client-0625573011/gwenlaya_v4/tpu_smoke/gwenlaya-tpu-smoke-215529/}).
The first, on a spot VM, was preempted after about 4 minutes with no results. The second, on
demand, gave the results below. The Qwen3.5 item is \textbf{updated in v3.3.1}: it described run
\#1 only, and run \#3 (Section~\ref{sec:tpurun}) shows that Qwen3.5 does generate on one v5e chip.

\begin{itemize}
\item \textbf{Qwen2.5 works.} \code{Qwen/Qwen2.5-Coder-1.5B-Instruct} loaded and generated with
  vLLM~\cite{vllm} 0.31.0's TPU backend (load 208.9 s; 442 completion tokens in 0.61 s,
  724.6 tok/s batched throughput; \code{res_qwen25.json}). The GWAYA gate on that VM returned UNVERIFIED for
  every item because bubblewrap was not available there, i.e.\ it failed closed as designed; no
  correctness number came out of this run.
\item \textbf{Qwen3.5 generates on TPU with lazy compilation (updated).} In run \#1,
  \code{Qwen/Qwen3.5-4B} resolved to \code{Qwen3_5ForConditionalGeneration} but did not finish
  loading/compiling within the 1,500 s step limit (exit 124). Qwen3.5 is not JAX-native in
  tpu-inference and runs through the PyTorch fallback; it runs when the up-front precompilation is
  skipped (\code{SKIP_JAX_PRECOMPILE=1}). With that setting, Qwen3.5-2B and Qwen3.5-4B generated all
  80 night tasks in run \#3 (Section~\ref{sec:tpurun}); in run \#2 Qwen3.5-0.8B also generated 16
  night tasks (\code{results/gwenlaya_v4/tpu_run2/status.jsonl}); run \#2 scores are not used, because
  its Python scoring was invalid (D29).
\item \textbf{No TPU LoRA path was found for Qwen3.5 dense or Qwen3.8.} Serving Qwen2.5 with
  \code{enable_lora} failed at engine initialisation. The JAX training stacks we inspected list
  Qwen2/Qwen3 (Tunix 0.1.7) and Qwen2.5/Qwen3 plus Qwen3.5 mixture-of-experts scripts (MaxText), but
  no dense Qwen3.5 or Qwen3.8 path. GwenLaya's training steps (Laya head, SFT) therefore stay on the
  GPU/CPU plan. This is unchanged in v3.3.1.
\end{itemize}

\section{Limitations}\label{sec:limits}

\begin{itemize}
\item No pre-registered test ran. Nothing here supports or refutes H1--H12, H14 or H15.
\item The only scored arm is unregistered, single-seed, $n=80$, on CPU, with no gate recorded.
\item The night math generations are invalid (prompt-path defect, D28); under the registered
  boxed-only rule none passes. Python ($n=28$) and Rust ($n=26$) are usable descriptive results
  only; the Python AUROC interval includes 0.5, and Rust has 6 passing items.
\item The v3.3.0 Rust result was a harness artefact (D27). The fixed Rust harness was validated after
  the generations existed, on 25 hand-written correct and 9 hand-written wrong solutions written for
  this purpose; it has not been checked against an independent reference set, and one of the 26
  night Rust tasks has no reference solution in the validation.
\item The TPU run (Section~\ref{sec:tpurun}) is unregistered, single-sample, without
  log-probabilities, gate or calibration; its TPU-host Python scores were invalid and all its rows
  were re-scored off the TPU host. Math truncations at 1,024 tokens count as UNVERIFIED.
\item \textbf{Contamination.} All absolute scores are on public sets (HumanEval+, MBPP+,
  MultiPL-E, MATH-500) that Qwen3.5 has probably seen in pretraining; they are not clean capability
  estimates, and only paired within-model deltas are claimed by the registration. Decontamination
  (D18) covered only training/calibration data against E and cannot detect pretraining exposure. The
  contamination-stratified analysis asked for by review finding F12 (for example MBPP+ versus
  HumanEval+ items, or a post-cutoff anchor such as LiveCodeBench, which D10 dropped) was not done:
  \TBD.
\item The HumanEval+ gate payloads of the night task files contained the hidden tests (D25). No gate
  ran in L2, so no result is affected, but any earlier claim that the gate never saw the scoring
  checks was false for those files.
\item Several deviations (D22--D30) were written after the L2 generations existed; none was written
  after a registered test, because none ran.
\item Even with all arms present, $n=80$ gives H1 power of about 0.05 at its MEI; the night design
  could at best produce an inconclusive H1.
\item Cost is server CPU-seconds on a machine shared with foreign jobs and includes idle threads; it
  is not comparable to the registered L4 GPU-seconds.
\item The USD spend is a list-price estimate, not the billed amount, and H13 holds largely by
  construction of the ledger.
\item Scored rows are not yet mirrored to the data lake as the registration requires.
\item Lean 4, the training arms, quantization and the endpoint were not run. The TPU findings are
  from one chip and one vLLM version.
\end{itemize}
